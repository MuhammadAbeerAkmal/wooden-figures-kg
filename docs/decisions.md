# Design decisions

Each entry gives the decision, the reason, the alternative that was considered,
and the price of the choice. Where a simpler CIDOC-CRM form was chosen over a
fuller one, the entry says so under **Trade-off** and names the fuller form.

## Relational model

### 1. SQLite, not MySQL

**Decision.** SQLite through the `better-sqlite3` driver.

**Why.** The data set has 84 rows and one writer. SQLite needs no server, no
credentials and no extra container, so `docker compose up` stays fast and the
tests run against an in-memory database in milliseconds. It supports
everything the project needs: foreign keys, CHECK constraints and recursive
common table expressions.

**Alternative.** MySQL in Docker. It would add a container, a health check, a
password and a startup delay, and would demonstrate nothing extra about data
modelling.

**Price.** SQLite types are loose (a `varchar(16)` length is not enforced), and
it is not a multi-user server. TypeORM hides the dialect, so moving to MySQL or
PostgreSQL would mean changing the driver settings and regenerating the
migration.

### 2. A migration plus a seed script, not `synchronize: true`

**Decision.** The schema is created by a TypeORM migration. The data is
inserted by a separate, idempotent seed function.

**Why.** A migration is the schema written down as reviewable SQL. This is how
a real project changes a database. `synchronize` changes tables silently
whenever an entity changes. Keeping the seed apart separates structure from
content.

**Detail.** The migration was generated by TypeORM and then tidied by hand,
because the generator writes every SQLite table twice. The constraint names are
the generated ones on purpose: TypeORM compares names, and
`npm run migration:generate` reports "no changes", which proves the migration
and the entities agree.

### 3. Third normal form with one table per vocabulary

**Decision.** `material`, `object_type`, `period`, `site` and `collection` are
tables. `figure` refers to them by foreign key.

**Why.** Each fact is stored once. Renaming a material is one update. The
foreign key guarantees that a figure cannot refer to a material that does not
exist. `ON DELETE RESTRICT` stops a vocabulary term in use from being deleted.

**Why `condition` is different.** The four condition values are a
`CHECK` constraint on a text column, not a table. They are a fixed grading
scale with no attributes of their own, so a lookup table would add a join and
nothing else. Showing both techniques side by side is also deliberate.

### 4. Condition reports in their own table

**Decision.** `condition_report` has a foreign key to `figure` (one figure,
many reports), with `ON DELETE CASCADE`.

**Why.** An object is assessed repeatedly, and its condition changes. A
`condition` column on `figure` could hold only the latest value and would lose
the history. A report cannot exist without its figure, hence the cascade.

### 5. Places as a self-referencing hierarchy

**Decision.** `site.parent_id` points to another row of `site`
(Egypt, region, site, part of a site).

**Why.** Real place data is hierarchical, and the depth is not fixed. This is
the classic adjacency list. It gives competency question 5 a real reason to
exist: SQL needs a recursive CTE where SPARQL needs a property path.

**Alternative.** Fixed columns `region` and `country` on `site`. Simpler to
query, but it breaks as soon as a place has a different number of levels.

### 6. A `slug` on every vocabulary row

**Decision.** Every vocabulary table has a unique, readable `slug`
(`sycamore-fig`, `middle-kingdom`) next to the numeric `id`.

**Why.** The `id` is an auto-increment number that can differ between
databases. The slug is stable. API filters use it, and the RDF mapping builds
URIs from it, so a URI never changes because rows were inserted in a different
order.

## CIDOC-CRM model

### 7. CIDOC-CRM 7.1.3, with every term checked by a test

**Decision.** The mapping follows version 7.1.3 and uses the names of its
official RDFS file, for example `crm:E22_Human-Made_Object` and
`crm:P108i_was_produced_by`.

**Why.** 7.1.3 is a current official release with a published RDFS. Class and
property names changed between versions (E22 was "Man-Made Object" before
version 7), so guessing names is risky.

**How it is verified.** The RDFS file is stored unchanged in `vocab/`.
`crm-terms.spec.ts` checks that each of the 12 classes and 19 properties the
project uses is declared in that file, and that the SHACL shapes use no other
CRM term. TypeScript union types make a misspelled term a compile error.

**Limit.** The test proves the terms exist. It cannot prove they are used with
the right meaning. Domains and ranges were checked by hand against the RDFS
(see decision 18).

### 8. The classes, and why twelve instead of six to eight

**Decision.** Eight core classes and four supporting ones.

| Class | Why it is needed |
| --- | --- |
| E22 Human-Made Object | The figure. The standard class for an object made by people. |
| E12 Production | CRM dates events, not objects. The dating needs an event to belong to. |
| E52 Time-Span | Periods, acquisition years and assessment dates. |
| E53 Place | Find sites and the regions that contain them. |
| E57 Material | Wood species. |
| E55 Type | Every controlled term: object type, condition, kind of dimension. |
| E8 Acquisition | "Previous owner" is a change of ownership, which CRM models as an event. |
| E3 Condition State | One condition report. |
| E42 Identifier | The inventory number. `P48 has preferred identifier` must point to an E42. |
| E39 Actor | `P23 transferred title from` must point to an actor. |
| E54 Dimension | `P43 has dimension` must point to an E54. CRM has no "height" property. |
| E58 Measurement Unit | `P91 has unit` must point to an E58. |

**Why not eight.** The brief asked for about six to eight classes. Staying at
eight would have meant either dropping data from the graph (inventory number,
dimensions, previous owner) or attaching literals with properties that do not
allow it. A graph that holds less than the table would make the comparison
unfair, and wrong ranges would make the model invalid CIDOC-CRM. The four
supporting classes are each a single node type with two or three properties.

### 9. Dating through a production event

**Decision.** `figure P108i was produced by → E12 Production → P4 has
time-span → the period`.

**Why.** This is the central idea of CIDOC-CRM. An object has no date. Things
happen to it, and those events have time-spans. It also removes an ambiguity in
the table: `period_id` does not say whether the figure was made, used or buried
then. The event says: made.

**Price.** One extra node and one extra step in every query about dating.

### 10. Previous owner through an acquisition event

**Decision.** `figure P24i changed ownership through → E8 Acquisition`, with
`P23 transferred title from` the previous owner, `P22 transferred title to`
the museum, and `P4 has time-span` the acquisition year.

**Why.** The table says "this figure is linked to that collection". The event
says who gave up ownership, who received it and when. A second or third change
of owner would be another event, with no change to the model. In the table it
would need a new provenance table.

**Trade-off.** `collection` rows are mapped to **E39 Actor**. The column is
described as "previous owner or collection", which mixes two ideas: an owner
(an actor) and a collection (a set of objects, `E78 Curated Holding`). Actor
was chosen because the property `P23` requires one. For a private collector or
a dealer this is right. For an institutional collection, the precise model
would be the owning institution as actor, and the collection as a curated
holding.

### 11. Find site as P53 has former or current location

**Decision.** `figure P53 has former or current location → E53 Place`.

**Why.** It is true (the object was at that place), it is in base CIDOC-CRM,
and it needs no extra class.

**Trade-off.** P53 does not say "found at". Base CRM has no find event. The
precise options are an `S19 Encounter Event` from the CRMsci extension, or a
generic `E7 Activity` typed "find" with `P7 took place at`. Either adds a class
and an event node per figure. A query cannot tell a find site from any other
former location with the current model. For a real archaeological data set this
would be the first thing to improve.

### 12. Period as E52 Time-Span, not E4 Period

**Decision.** A row of `period` becomes one shared `E52 Time-Span` with a
label and two bounds. The production event points to it.

**Why.** The project uses a period only as a date range, and the brief named
E52. This saves a class.

**Trade-off.** "Middle Kingdom" is a cultural and historical period, which
in CRM is an `E4 Period` that has its own time-span. The fuller model is
`production P10 falls within → E4 Period → P4 has time-span → E52`. Labelling a
time-span "Middle Kingdom" blurs the period with its dates. It also means many
productions share one time-span node, which reads as "all made in exactly the
same span" rather than "each made at some time within it". The `P82a` and
`P82b` bounds (earliest start, latest end) make the second reading the
intended one.

### 13. Condition as E3 Condition State with its date attached

**Decision.** `figure P44 has condition → E3 Condition State`, with
`P2 has type` (good, fair, poor, fragmentary), `P3 has note` and
`P4 has time-span` for the assessment date.

**Why.** E3 is the class for the state of an object during a time. Its scope
note allows the asserted time-span to be shorter than the real one, so a
one-day span for "seen in this state on this day" is acceptable.

**Trade-off.** The act of assessing is an `E14 Condition Assessment`
(`P34 concerned` the object, `P35 has identified` the state). The date strictly
belongs to that activity. It was left out to save a class, and because the data
does not record who made the assessment.

### 14. Dimensions as E54 nodes

**Decision.** One `E54 Dimension` per measured value, with `P2 has type`
(height, width, depth), `P90 has value` as `xsd:decimal`, and `P91 has unit`
centimetre.

**Why.** CRM has no shortcut property for a measurement. The node keeps the
number, the unit and the kind together, where the table hides the unit and the
kind in the column name `height_cm`.

**Price.** Five triples for one number. This is the clearest case of CRM being
verbose, and competency question 2 shows what it costs in a query.

### 15. Types as a small thesaurus

**Decision.** All controlled terms are `E55 Type`. Each group has a broader
term: `type:servant-figure P127 has broader term type:object-type`.

**Why.** Without the grouping, a condition term could be used as an object
type and still be an E55. The broader term lets a SHACL shape require that a
figure's type comes from the object type branch.

**Alternative.** Local subclasses of E55 (`ex:ObjectType`). That is also
accepted practice, but it adds classes outside the standard.

### 16. `rdfs:label` for names, `skos:altLabel` for scientific names

**Decision.** Titles and vocabulary names are `rdfs:label`. The scientific name
of a wood species is `skos:altLabel`.

**Why.** The CRM guidelines for RDF recommend `rdfs:label` for a display name.
The full CRM form (`P102 has title → E35 Title`, or `P1 is identified by →
E41 Appellation`) adds a class and a node without adding information here.
SKOS is the usual companion vocabulary for thesauri.

**Trade-off.** A purist CRM model would use E35 and E41. A better model for
species would link each material to an external authority (see "Left out on
purpose").

### 17. Years as `xsd:gYear`

**Decision.** Period bounds and acquisition years are `xsd:gYear`
(`"-2055"^^xsd:gYear`). Assessment dates are `xsd:date`.

**Why.** The source data has years, not days. `xsd:gYear` says so honestly,
where `-2055-01-01` would claim a precision that does not exist.

**Trade-off.** BCE years have a known trap. In XSD 1.0 there is no year
zero and `-2055` is 2055 BCE. In XSD 1.1 and ISO 8601 there is a year zero and
`-2055` is 2056 BCE. This project means 2055 BCE, as in the SQL column. With
approximate period dates one year does not matter, but an exchange format must
state its convention. Also, SPARQL engines are not required to order `gYear`
values, so date range filters would need care.

### 18. One direction per relationship, no inference

**Decision.** Each relationship is stored once, in the direction that starts at
the figure where possible: `P108i was produced by` (object to event), not also
`P108 has produced`.

**Why.** Everything about a figure is then reachable by following links
outwards from it. That keeps the SHACL shapes, the Turtle of one figure and the
SPARQL queries simple. Oxigraph does no reasoning, so a triple that is not
stored does not exist. Storing both directions would double the event triples
and create two things to keep in step.

**Domains and ranges checked by hand** against the RDFS of 7.1.3:

| Property | Domain → range |
| --- | --- |
| P2 has type | E1 CRM Entity → E55 Type |
| P3 has note | E1 CRM Entity → literal |
| P4 has time-span | E2 Temporal Entity → E52 Time-Span |
| P22 transferred title to, P23 transferred title from | E8 Acquisition → E39 Actor |
| P24i changed ownership through | E18 Physical Thing → E8 Acquisition |
| P43 has dimension | E70 Thing → E54 Dimension |
| P44 has condition | E18 Physical Thing → E3 Condition State |
| P45 consists of | E18 Physical Thing → E57 Material |
| P48 has preferred identifier | E1 CRM Entity → E42 Identifier |
| P53 has former or current location | E18 Physical Thing → E53 Place |
| P82a begin of the begin, P82b end of the end | E52 Time-Span → literal |
| P89 falls within | E53 Place → E53 Place |
| P90 has value | E54 Dimension → literal |
| P91 has unit | E54 Dimension → E58 Measurement Unit |
| P108i was produced by | E24 Physical Human-Made Thing → E12 Production |
| P127 has broader term | E55 Type → E55 Type |
| P190 has symbolic content | E90 Symbolic Object → literal |

E22 is a subclass of E24, E18 and E70; E12 and E8 are temporal entities; E3 is
a temporal entity; E42 is a symbolic object. So every use fits.

## RDF tooling

### 19. Oxigraph as the triplestore

**Decision.** Oxigraph server in Docker, used only through its HTTP endpoints.

**Why.** It is a single small binary that starts almost at once, implements
SPARQL 1.1 including property paths, and speaks the standard SPARQL Protocol
and Graph Store Protocol. Because only standard HTTP is used, another store
could replace it by changing one URL.

**Alternatives.** Apache Jena Fuseki (mature, but a JVM and more
configuration), GraphDB (has inference, but heavier and partly commercial).

**Price.** No reasoning. Subclass and inverse-property inference are not
available, which is why decision 18 matters.

### 20. SQLite is the source of truth; the graph is rebuilt on start

**Decision.** The API converts the relational data and replaces the default
graph in Oxigraph every time it starts. Oxigraph has no volume.

**Why.** Two stores that are edited separately drift apart. With one source and
one mapping function the graph cannot contain anything the tables do not. It
also makes the comparison meaningful: both models hold the same facts by
construction.

**Price.** The graph is read-only in practice. A real system with edits on both
sides would need synchronisation, which is a hard problem and out of scope.

### 21. The mapping is a set of pure functions

**Decision.** `mapper.ts` turns entities into triples with no database or
network access.

**Why.** It can be unit tested directly, it reads top to bottom next to
`mapping.md`, and the same code serves the export script, the loader and the
API.

**Alternative.** A declarative mapping language such as R2RML or RML. That is
the standard answer for large mappings and worth naming in a discussion. For
seven tables, one TypeScript file of about 200 lines is easier to read and to
test.

### 22. `n3` for RDF, `fetch` for SPARQL

**Decision.** The `n3` library builds, parses and writes RDF. SPARQL goes
through Node's built-in `fetch` in a client of about 60 lines.

**Why.** The SPARQL Protocol is a POST with a query and an `Accept` header. A
client library would add a dependency to save very little code, and writing it
shows the protocol is understood.

### 23. SHACL shapes mirror the relational constraints

**Decision.** `shapes/figure.shacl.ttl`, validated with `rdf-validate-shacl`.

| Relational constraint | SHACL equivalent |
| --- | --- |
| `NOT NULL` | `sh:minCount 1` |
| a single column (one value) | `sh:maxCount 1` |
| foreign key | `sh:class` (the target must exist and have the right type) |
| `CHECK (condition IN (...))` | `sh:in ( ... )` |
| `CHECK (height_cm > 0)` | `sh:minExclusive 0` |
| column type | `sh:datatype` |
| `height_cm NOT NULL`, the others nullable | `sh:qualifiedValueShape` with `sh:qualifiedMinCount 1` |
| (no equivalent) | `sh:pattern "^WF-[0-9]{4}$"` on the inventory number |

**Why.** RDF has an open world: missing data is not an error and any triple is
accepted. SHACL adds the closed-world checks that make data fit for an
application. The tests include data that must be rejected, to prove the shapes
do something.

**Difference that matters.** The database refuses a bad write. SHACL reports a
bad graph after the fact. Validation has to be run, here by
`npm run rdf:validate` and by the tests.

**Not covered.** Uniqueness of the inventory number across figures. SHACL Core
has no uniqueness constraint; it would need SHACL-SPARQL.

### 24. The form is generated from the same shapes

**Decision.** The data entry page uses the `@ulb-darmstadt/shacl-form` web
component with the shapes file and the vocabulary triples. The server
validates the result again. Nothing is saved.

**Why.** One definition drives both validation and the form, so they cannot
disagree. It is loaded only when the page is opened, because the component is
large (about 600 kB).

**Known limits.** The "Object type" dropdown lists every E55 Type, including
condition terms, because `sh:class` matches on `rdf:type` and CRM types are
instances of one class. The broader-term shape rejects a wrong choice on
validation. Saving is not implemented: it would need a reverse mapping from
triples to rows, plus authentication.

## Comparison engine

### 25. Six questions, each with identical output columns

**Decision.** Every question defines its columns once. The SQL and the SPARQL
version must both return them, and the engine reports whether the rows match.

**Why.** A comparison is only fair if both queries answer the same question.
Requiring identical rows turns that into something a test can check. The
questions were chosen to cover different shapes: filter, attributes,
self-join, aggregation, recursion, and alternative links.

**Change from the brief.** The example "figures connected via shared site and
period" became question 6, which covers shared site, period, material or owner
for one figure. It shows the same idea and makes the difference between the
models clearer. Height was added to question 2 so that at least one question
shows the cost of a CRM dimension node.

### 26. SQL through the TypeORM query builder, with two honest exceptions

**Decision.** All six SQL versions use the query builder. Question 5 passes a
raw SQL string for the recursive part, and question 6 joins four generated
statements with `UNION ALL` as text.

**Why.** The query builder has no API for recursion or for `UNION`. Hiding that
would misrepresent the comparison, so both are commented in the code and
discussed in `comparison.md`. Values are always bound parameters. The SQL shown
in the UI has the parameters written in for reading only.

### 27. Timings are a median of five runs, with a caveat

**Decision.** Each query runs five times and the median is reported, together
with a note.

**Why.** A single run mostly measures warm-up. Even so, the numbers compare an
in-process SQLite call with an HTTP request to another container, on 25
figures. They show overhead, not scalability, and the UI and the docs say so.

## Application

### 28. NestJS 12 as native ES modules, and the Node test runner

**Decision.** The API is written as ES modules (`"type": "module"`), compiled
with `tsc`, and tested with `node --test`.

**Why.** NestJS 12 is published as ES modules only, and so is
`rdf-validate-shacl`. Jest still needs experimental flags and extra
configuration for ES modules. The built-in test runner needs no dependency and
runs the same compiled code that runs in production.

**Price.** Relative imports carry a `.js` extension, and development uses
"compile, then run" instead of a TypeScript loader.

### 29. One NestJS module

**Decision.** All controllers and services are registered in `AppModule`. The
code is still split into folders by concern.

**Why.** Four controllers and five services do not need module boundaries.
Splitting them would add files without adding clarity.

### 30. A small UI with no component library

**Decision.** React, React Router and plain CSS with variables. Syntax
highlighting is a tokenizer of about 80 lines.

**Why.** The UI presents the models; it is not the subject. A component
library or a highlighting library would outweigh the code that uses it.
Filters are stored in the URL, so a filtered list or a chosen question can be
linked.

**Accessibility.** Semantic landmarks, a skip link, labels on every control,
table headers with scope, visible focus, status messages announced to screen
readers, scrollable regions reachable by keyboard, and light and dark colour
schemes. An end-to-end test checks that the page does not scroll sideways on a
phone-sized screen.

### 31. The figure's Turtle is read from the triplestore

**Decision.** The detail page gets its Turtle from a `CONSTRUCT` query to
Oxigraph (the figure and everything up to three links away), not by running
the mapper again.

**Why.** The page then shows what the knowledge graph really holds. A
triplestore returns triples in no order, so they are sorted for reading: the
figure first, then each node after the node that links to it, with the type and
label first.

### 32. nginx in front, so no CORS

**Decision.** In Docker, nginx serves the built UI and forwards `/api` to the
API. In development, Vite does the same.

**Why.** The browser talks to one origin, so the API needs no CORS
configuration.

## Out of scope

The project is complete within its scope: one fictional collection, modelled
twice and compared. The following belong to a production system, not to this
comparison.

- **Links to external authorities.** Materials and types to the Getty AAT,
  places to Pleiades or Wikidata, species to a taxonomic authority. This is
  where a knowledge graph pays off most. Every such identifier must be checked
  one by one, and a wrong one would be an invented fact.
- **A find event, E4 Period and E14 Condition Assessment**, the fuller forms
  named in decisions 11 to 13.
- **Provenance of statements.** Who recorded a dating, and on what evidence.
  CIDOC-CRM has `E13 Attribute Assignment` for this.
- **Named graphs** to separate the vocabulary, the objects and their sources.
- **Writing to the graph**, authentication and saving the SHACL form.
- **A declarative mapping** in RML or R2RML.
- **Benchmarks at a realistic size.** The timings here say nothing about
  100,000 objects.
